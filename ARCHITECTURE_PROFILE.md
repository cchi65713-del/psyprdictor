Purpose
-------
This document defines the canonical psychological constructs used by PsyPredictor, their canonical field names, owning modules (single-writer policy), data types, timescales, update rules, and permitted influence edges. The goal is to prevent conceptual overlap and accidental double-counting as the system grows.

Guiding principles
------------------
- Single-writer: each canonical field has one owning module that performs updates.
- Naming prefixes: `trait_`, `value_`, `belief_`, `need_`, `goal_`, `identity_`, `mem_`, `habit_`, `state_`.
- Timescale explicitness: annotate whether a field is `stable`, `slow`, `medium`, `fast`, or `contextual`.
- Evidence metadata: supporting evidence entries must use a canonical format: `{source: str, id: str, weight: float, timestamp: iso}`.
- Read/Write graph: document allowed read/write edges. Writes are restricted to owners.

Canonical constructs and mappings
--------------------------------

1) Personality (Traits)
- Canonical field: `trait_personality` (dict of trait_name -> float)
- Owner module (single-writer): `person_state` (setter APIs) / high-level personality updater
- Type: JSON object / dict[str, float] (0.0-1.0)
- Timescale: `stable` (months → years)
- Update rule: human-set or explicit slow update API; requires explicit evidence and audit trail. No automatic writes from reactive modules.
- Influence outputs: `trait_biases` vector used by perception, appraisal, learning-rate modifiers, and action-threshold adjusters.
- Notes: Do NOT use trait values directly as goal or habit values. Traits are priors only.

2) Values
- Canonical field: `value_weights` (list of {id, weight}) or dict[value_id -> float]
- Owner module: `person_state` (values API)
- Type: dict[str, float] or list of tuples
- Timescale: `slow` (months → years)
- Update rule: explicit update or slow learning pipeline with high evidence requirement
- Influence outputs: used by Goal Generator to produce prioritized goals and by appraisal to weight interpretations
- Notes: Values are upstream of goals and distinct from needs; keep them as evaluative priorities.

3) Beliefs (Long-term) & Expectations (Short-term)
- Canonical fields:
  - `beliefs` : dict[proposition_id -> {prob: float, conf: float, evidence: [e]}]  (long-term causal/semantic beliefs)
  - `expectations` : dict[prediction_id -> {prob: float, horizon, source} ] (short-horizon predictive estimates)
- Owner modules: `system_memory` / `pattern_learner` update beliefs; `prediction_fusion` or `perception` compute expectations
- Type: structured dicts with numeric probs and confidence
- Timescale: beliefs `medium` (days→months), expectations `fast` (seconds→minutes)
- Update rule: PatternLearner/memory informs beliefs through a canonical belief-update API (single path). Expectations produced on-demand from beliefs + current state.
- Influence outputs: used by action-value estimation, appraisal, and goal evaluation
- Notes: Do not have modules keep separate predictive caches that are also written; route all learning updates through the beliefs API.

4) Needs / Motivations
- Canonical field: `need_state` (dict[need_id -> urgency float])
- Owner module: `person_state` (or `motivation` manager)
- Type: dict[str, float]
- Timescale: `contextual` → `medium` (minutes→days)
- Update rule: physiological inputs, appraisal outputs, and scheduled tasks can update urgency; learning modifies thresholds slowly
- Influence outputs: priority scores passed to Goal Generator
- Notes: Needs are internal pressure signals that lead to goal instantiation; they are distinct from values which order goals.

5) Goals
- Canonical field: `active_goals` (list of goal objects)
- Owner module: `goal_manager` (new or extend `person_state.goals`)
- Type: list[{id, description, priority, deadline, origin:{value|need|identity}, status}]
- Timescale: `fast` → `medium` (minutes→days)
- Update rule: generated by Goal Generator from values/needs/identity; removed on completion or override; can be reprioritized.
- Influence outputs: each goal produces a `BehavioralTendency` proto when evaluated (source='goal_directed')
- Notes: Goals are explicit objects; avoid storing same content in `values` or `needs` fields.

6) Identity / Self-concept
- Canonical field: `identity_schema` (dict[role_id -> {importance,float,standards:[str]}])
- Owner module: `person_state.identity` (with richer schema)
- Type: structured dict/list
- Timescale: `medium` → `slow`
- Update rule: explicit API or narrative-learning pipeline; context activation produces active facets
- Influence outputs: constraints on goal acceptability, weighting in appraisal and decision thresholds
- Notes: Identity is not personality nor just a value; it constrains what actions are permissible or self-consistent.

7) Memory / Experience
- Canonical fields:
  - `mem_episodic` : list[Experience] (timestamped records)
  - `mem_semantic` : dict[fact_id -> info]
  - `pattern_stats` : module `PatternLearner` summaries (pattern_id -> {outcome_counts, recency_weighted})
- Owner modules: `Memory` (episodic store) and `PatternLearner` (statistical summaries)
- Type: objects + indexed stores
- Timescale: storage long-lived; retrieval contextual
- Update rule: `Memory.store(exp)` appends and (if connected) triggers `PatternLearner.learn(...)`; PatternLearner is the canonical summarizer
- Influence outputs: pattern statistics feed habit formation and belief updates
- Notes: Memory is the canonical historical record; pattern summaries are the canonical statistics used elsewhere. Do not let other modules independently re-summarize and write back differing statistics.

8) Habits
- Canonical field: `habit_strength` (dict[pattern_id -> dict[action -> strength_float]])
- Owner module: `habit_formation.update_habit_strengths` (single-writer)
- Type: nested dict
- Timescale: `medium` (repetition dependent, days→months)
- Update rule: only `habit_formation` computes strengths from `pattern_stats` and writes to `person_state.habit_strength`
- Influence outputs: `propose_habitual` reads `habit_strength` and generates BehavioralTendencies (source='habitual')
- Notes: Habits are learned automatic tendencies derived from memory statistics; they are not personality.

9) Momentary State (Appraisal, Emotion, Arousal, Regulation, Metacognition)
- Canonical fields (split `state_of_mind` into):
  - `state_appraisal` : dict[appraisal_dim -> score]
  - `state_emotion` : list[{label, intensity}]
  - `state_arousal` : float
  - `state_regulation` : float (executive resource / inhibition capacity)
  - `state_meta_confidence` : float (metacognitive confidence about beliefs/decisions)
- Owner module: `state_manager` / `person_state` runtime updates
- Type: scalars and small dicts
- Timescale: `fast` (seconds→hours)
- Update rule: appraisal module writes appraisals; perception and state inference update `state_appraisal`/`state_emotion`; explicit decay rules apply to transient items
- Influence outputs: used by `propose_reactive`, threshold modulation for competition, and learning-rate gating
- Notes: Avoid using `state_of_mind` as a catch-all; split by function to avoid double-count.

Decision & Competition contracts
------------------------------
- All subsystems expose proposals as `BehavioralTendency` objects with fields: `action`, `raw_strength`, `source`, `supporting_evidence` (canonical form), `confidence_in_proposal`, `context_tags`.
- `CompetitionEngine` normalizes and composes these tendencies. It must treat `confidence_in_proposal` as a local, subsystem-assigned number and use canonical evidence counts rather than raw memory counts.

Allowed read/write edges (one-line summary)
- Memory (`Memory`) can be written by any experience-producing module (LearningBridge) and read by PatternLearner, habit_formation, and belief-updater.
- PatternLearner writes `pattern_stats` only; habit_formation reads `pattern_stats` and writes `habit_strength` only.
- PatternLearner may propose belief updates via a belief-update API in `system_memory`, but only that API mutates `beliefs` (single-writer semantics).
- Goal_Generator reads `value_weights`, `need_state`, `identity_schema`, and `beliefs` and writes `active_goals`.
- Reactive proposer (`propose_reactive`) reads `state_*` and `trait_personality` but does not write traits/values.

Anti-double-count rules (enforceable checks)
-----------------------------------------
1. Single-writer assertions: unit tests to ensure only the owner module modifies canonical fields (e.g., `habit_strength` modified only by `habit_formation`).
2. Evidence canonicalization: require `supporting_evidence` entries follow the schema and include `source` and `id` so `CompetitionEngine` can deduplicate evidence from `Memory` vs `PatternLearner`.
3. Naming enforcement: lint rule that flags ambiguous names (`preferences` vs `values`) and requires prefixing.
4. Edge policy tests: graph-based tests that verify only allowed edges perform writes during integration tests.

Example APIs (specs, not implementation)
--------------------------------------
- `Memory.store(experience)` — appends experience and triggers pattern learning if connected.
- `PatternLearner.get_pattern_stats(pattern_id)` — returns `{outcomes: {B1:3, B4:1}, recency_score:0.8}`
- `habit_formation.update_habit_strengths(person_state, memory, pattern_learner, pattern_id)` — computes and writes `person_state.habit_strength[pattern_id]`
- `BeliefUpdater.update_from_pattern(pattern_stats)` — canonical belief update allowing controlled learning rates
- `GoalGenerator.generate_goals(values, needs, identity, beliefs)` — produces and registers `active_goals`

Testing checklist (before adding new layers)
-------------------------------------------
- Unit test: single-habit write test — ensure `habit_strength` only updated via `habit_formation`.
- Integration test: evidence dedupe — same evidence id from memory and pattern_learner counts once in competition evidence_score.
- Regression: ensure `state_of_mind` split does not change reactive behavior; update callers to use split fields.
